# Volumes & Bind Mounts

<Callout type="info">
Foundation mentioned this problem but did not solve it: remove a container, and anything that changed inside it is gone. This page shows the two ways Docker solves that.
</Callout>

## Proving the Problem

Run a plain container and create a file inside it:

```bash filename="Terminal"
docker run -d --name proof-container nginx
docker exec proof-container sh -c "echo hello > /tmp/note.txt"
docker exec proof-container cat /tmp/note.txt
```

You will see `hello` printed. Now remove the container and start a fresh one from the same image:

```bash filename="Terminal"
docker rm -f proof-container
docker run -d --name proof-container-2 nginx
docker exec proof-container-2 cat /tmp/note.txt
```

This fails — `note.txt` does not exist. The file only ever lived inside the first container's own temporary storage, which was deleted along with it.

## Two Ways to Keep Data Alive

Docker offers two mechanisms that both work by connecting a container to storage that survives outside of it. They differ in **where** that storage lives.

| | Bind Mount | Named Volume |
|---|---|---|
| Storage location | A folder you choose, on your machine | A folder Docker manages for you |
| You can browse it directly | Yes — it is a real folder on your computer | Not easily — it lives inside Docker's own storage area |
| Typical use | Local development — editing source code live | Data that only the container needs, like a database's files |

<Callout type="default">
You will use named volumes properly once a database enters the picture in the next section. For a Next.js app on its own, a bind mount solves the more immediate problem: editing code and seeing changes without rebuilding the image every time.
</Callout>

## Bind Mount: A Live-Reloading Dev Container

Instead of rebuilding your image every time you change a line of code, you can mount your project folder straight into a container and run the Next.js dev server inside it.

<Steps>

### Run with a bind mount

From your project folder:

```bash filename="Terminal"
docker run -d -p 3000:3000 \
  -v "$(pwd)":/app \
  -v /app/node_modules \
  -w /app \
  --name next-dev \
  node:20-alpine \
  sh -c "npm install && npm run dev"
```

- `-v "$(pwd)":/app` — the bind mount. `$(pwd)` is your current folder on your computer; `/app` is where it appears inside the container. Changes on either side now show up on both.
- `-v /app/node_modules` — a second, separate volume just for `node_modules`. This is explained below — do not skip it.

<Callout type="default">
`$(pwd)` works in Git Bash, macOS, and Linux terminals. On Windows PowerShell, use `${PWD}` instead. On Command Prompt, use `%cd%`.
</Callout>
- `-w /app` — sets the working folder for the command that runs next.
- `sh -c "npm install && npm run dev"` — installs dependencies and starts the Next.js dev server, both inside the container.

### Confirm live reload works

Open [http://localhost:3000](http://localhost:3000). Now edit a page in your code editor, on your actual computer, and save it. The browser should update, exactly like running `npm run dev` outside Docker.

</Steps>

## Why `node_modules` Needs Its Own Line

If you only used `-v "$(pwd)":/app` without the second line, your bind mount would also overwrite the container's `/app/node_modules` with whatever `node_modules` exists on your computer — or nothing, if you have not run `npm install` locally.

This causes a real problem: some packages contain native code compiled specifically for your computer's operating system. A version built on Windows or macOS will not run correctly inside the Linux container.

`-v /app/node_modules` creates a separate, anonymous volume just for that one folder. It "shields" `/app/node_modules` from the bind mount above it, so the container keeps its own Linux-compatible copy, installed by `npm install` running inside the container itself.

<Callout type="warning">
This is one of the most common real-world Docker + Node.js mistakes: a bind-mounted `node_modules` that was installed on the host, silently breaking inside the container. Keep this second line even if it looks redundant.
</Callout>

## Hands-on Task

1. Run your Next.js app with the bind-mount command above.
2. Confirm `localhost:3000` loads.
3. Edit some visible text in a page component, save, and confirm it updates without restarting the container.
4. Stop and remove the container, then run it again — confirm your code changes are still there (because they live on your computer, not inside the container).
