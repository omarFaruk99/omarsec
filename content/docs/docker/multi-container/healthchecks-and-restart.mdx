# Health Checks & Restart

<Callout type="info">
Two small additions make your stack noticeably more reliable: proving a service is really ready, not just started, and telling Docker to bring a crashed container back on its own.
</Callout>

## The Gap `depends_on` Leaves

On the last page, `depends_on` made `api` wait for `db`'s **container** to start. But a container starting is not the same as PostgreSQL being **ready to accept connections** — there is a brief window where the container is running but the database inside it is still initializing.

Most of the time this window is short enough that you never notice. Occasionally, `api` starts just fast enough to hit that gap, and its first connection attempt fails.

## Health Checks

A **health check** is a command Docker runs periodically, inside the container, to decide whether the service is actually working — not just running.

```yaml filename="compose.yaml"
db:
  image: postgres:16-alpine
  environment:
    - POSTGRES_USER=appuser
    - POSTGRES_PASSWORD=secret
    - POSTGRES_DB=appdb
  volumes:
    - db-data:/var/lib/postgresql/data
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U appuser"]
    interval: 5s
    timeout: 5s
    retries: 5
```

- `test` — the command Docker runs to check health. `pg_isready` is a small tool built into the Postgres image specifically for this.
- `interval` — how often to check.
- `timeout` — how long to wait for the check itself before considering it failed.
- `retries` — how many failed checks in a row before marking the service "unhealthy".

Check it directly:

```bash filename="Terminal"
docker compose ps
```

The `STATUS` column now shows `healthy` once the check passes, not just `Up`.

## Making `depends_on` Wait for Health

With a health check defined, `depends_on` can wait for real readiness instead of just container start:

```yaml filename="compose.yaml"
api:
  build:
    context: ./api
  environment:
    - DATABASE_URL=postgresql://appuser:secret@db:5432/appdb
  depends_on:
    db:
      condition: service_healthy
```

This is the same `depends_on` key as before, written in its longer form. Now `api` genuinely waits until `db` reports healthy, closing the gap from the start of this page.

## Restart Policies

Separately from startup order, you can tell Docker what to do if a container crashes, or if the machine itself restarts.

```yaml filename="compose.yaml"
api:
  restart: unless-stopped
```

| Policy | Behavior |
|---|---|
| `no` (default) | Never restart automatically |
| `always` | Always restart, even after an explicit manual stop, and when Docker itself restarts |
| `unless-stopped` | Restart automatically, unless you explicitly stopped it yourself |
| `on-failure` | Restart only if the container exited with an error |

<Callout type="default">
`unless-stopped` is a reasonable default for most services — it recovers from crashes, but respects you deliberately stopping something for maintenance.
</Callout>

## Putting It Together

```yaml filename="compose.yaml"
services:
  web:
    build:
      context: ./web
    ports:
      - "3000:3000"
    environment:
      - API_URL=http://api:4000
    depends_on:
      - api
    restart: unless-stopped

  api:
    build:
      context: ./api
    ports:
      - "4000:4000"
    environment:
      - DATABASE_URL=postgresql://appuser:secret@db:5432/appdb
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=appuser
      - POSTGRES_PASSWORD=secret
      - POSTGRES_DB=appdb
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser"]
      interval: 5s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  db-data:
```

## Hands-on Task

1. Add the health check to your `db` service, and switch `api`'s `depends_on` to the `condition: service_healthy` form.
2. Run `docker compose up` and watch `docker compose ps` — confirm `db` shows `healthy` before `api` starts.
3. Add `restart: unless-stopped` to all three services.
4. Test it: run `docker compose kill api` to simulate a crash, then check `docker compose ps` again — it should already be starting back up.
