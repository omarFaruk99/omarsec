# Secure the Server

<Callout type="info">
  App deploy করার আগে server secure করা **বাধ্যতামূলক**। এই page-এ শিখবেন নিরাপদ user তৈরি করতে, SSH key দিয়ে login করতে, password login বন্ধ করতে এবং firewall চালু করতে।
</Callout>

## Why Secure First?

**১. Non-root user (`queen`):** Root বা admin হিসেবে সরাসরি কাজ করা ঝুঁকিপূর্ণ। কারণ root হিসেবে একটি সামান্য টাইপিং ভুলে পুরো সার্ভার মুছে যেতে পারে। আমরা একটি সাধারণ ইউজার তৈরি করব যা প্রয়োজনে `sudo` দিয়ে admin-এর কাজ করতে পারবে।

**২. SSH Key Authentication:** পাসওয়ার্ডের চেয়ে SSH Key অনেক বেশি নিরাপদ। এটি একটি cryptographic key pair:
- **Private Key:** এটি আপনার নিজের চাবির মতো, যা শুধু আপনার নিজের কম্পিউটারে থাকবে। কাউকে এটি দেবেন না।
- **Public Key:** এটি একটি তালার মতো, যা আমরা সার্ভারে রেখে দেব।

সার্ভারে লগিন করার সময় আপনার কম্পিউটার নিজের Private key দিয়ে সার্ভারের Public key-এর সাথে ম্যাচ করে। এটি পাসওয়ার্ডের চেয়ে অনেক শক্তিশালী এবং হ্যাকারদের পক্ষে ব্রেক করা প্রায় অসম্ভব।

## Before You Start

<Callout type="info">
  নিচের ধাপগুলো **Contabo, DigitalOcean, AWS EC2 — সব provider-এর জন্যই এক**। শুধু **দুটি ধাপ** provider অনুযায়ী আলাদা: প্রথমে login করা, আর key copy করা। ওই দুটি ধাপে আপনার provider-এর অংশটুকু দেখে নেবেন।

  পার্থক্যের মূল কারণ — Contabo-তে আপনি সরাসরি `root` হিসেবে password দিয়ে ঢোকেন, আর AWS-এ `ubuntu` user হিসেবে একটি `.pem` key দিয়ে ঢোকেন।
</Callout>

<Steps>

### Login to Your Server

আপনার provider অনুযায়ী login করুন।

**Contabo বা সাধারণ VPS** — server তৈরির সময় পাওয়া root password দিয়ে:

```bash filename="LOCAL — Terminal"
ssh root@YOUR_SERVER_IP
```

**AWS EC2** — download করা `.pem` key দিয়ে, user হবে `ubuntu`:

```bash filename="LOCAL — Terminal"
ssh -i ~/.ssh/myapp-key.pem ubuntu@YOUR_EC2_IP
```

<Callout type="warning">
  Contabo-তে আপনি এখন `root` — অর্থাৎ সব permission আছে এবং একটি ভুল command পুরো server নষ্ট করতে পারে। AWS-এ আপনি `ubuntu` user, যার `sudo` access আছে।

  এই পার্থক্যের কারণে নিচের কিছু command-এ Contabo-তে `sudo` লাগবে না, কিন্তু AWS-এ লাগবে। যেখানে দরকার সেখানে বলে দেওয়া আছে।
</Callout>

### Create the queen User

সার্ভারে একটি নতুন ইউজার তৈরি করুন:

```bash filename="SERVER — Terminal"
sudo adduser queen
```

পাসওয়ার্ড সেট করুন এবং বাকি তথ্যগুলো Enter চেপে স্কিপ করুন। এখন এই ইউজারকে `sudo` পারমিশন দিন:

```bash filename="SERVER — Terminal"
sudo usermod -aG sudo queen
```

<Callout type="info">
  **`usermod -aG` কী করছে?**
  - `usermod` — User Modify, অর্থাৎ একটি বিদ্যমান user পরিবর্তন করা।
  - `-aG` — Append to Group। `a` না দিলে user তার আগের সব group থেকে বাদ পড়ে যাবে, যা একটি বিপজ্জনক ভুল।

  Contabo-তে আপনি root হিসেবে আছেন, তাই `sudo` ছাড়াও এই command চলবে। `sudo` থাকলে সমস্যা নেই — root-এর জন্য এটি উপেক্ষা করা হয়।
</Callout>

### Generate an SSH Key

এই ধাপটি **আপনার নিজের কম্পিউটারে** করতে হবে, server-এ নয়।

<Callout type="warning">
  আগে থেকে key থাকলে নতুন করে বানাবেন না — `ls ~/.ssh/id_ed25519` দিয়ে দেখুন। ফাইলটি থাকলে এই ধাপ skip করে পরের ধাপে যান। নতুন key বানালে পুরনোটি overwrite হয়ে যেতে পারে এবং অন্য যেসব server-এ ওই key ব্যবহার করছেন সেগুলোতে আর ঢুকতে পারবেন না।
</Callout>

```bash filename="LOCAL — Terminal"
ssh-keygen -t ed25519 -C "your_email@example.com"
```

কোথায় save করবে জিজ্ঞেস করলে Enter চাপুন (default location)। Passphrase দিতে পারেন বা খালি রাখতে পারেন।

**যা তৈরি হলো** — আপনার `~/.ssh/` folder-এ দুটি ফাইল:

1. **`id_ed25519`** (Private Key) — আপনার গোপন চাবি। কখনো কাউকে দেবেন না, কোথাও upload করবেন না।
2. **`id_ed25519.pub`** (Public Key) — এটিই আমরা server-এ পাঠাব।

<Callout type="default">
  **Pro Tip:** প্রফেশনাল environment-এ প্রতিটি developer-এর নিজস্ব আলাদা SSH key থাকে। এতে কে কখন server-এ login করেছে তা track করা যায়, এবং কারো access বাতিল করতে হলে শুধু তার key সরালেই হয়।
</Callout>

### Copy Your Key to queen

এবার আপনার Public Key `queen` user-এর কাছে পাঠাতে হবে। এই ধাপটি provider অনুযায়ী আলাদা।

<Callout type="info">
  **`ssh-copy-id` কী?** এটি আপনার public key-টি স্বয়ংক্রিয়ভাবে server-এর `~/.ssh/authorized_keys` ফাইলে যোগ করে দেয় — সঠিক permission সহ। হাতে করলে permission ভুল হওয়ার সম্ভাবনা থাকে, তাই এই tool ব্যবহার করাই ভালো।
</Callout>

**Contabo বা সাধারণ VPS** — সরাসরি `queen` user-এ key পাঠান:

```bash filename="LOCAL — Terminal"
ssh-copy-id -i ~/.ssh/id_ed25519.pub queen@YOUR_SERVER_IP
```

পাসওয়ার্ড চাইলে `queen`-এর পাসওয়ার্ড দিন। এই ধাপ শেষ, পরের ধাপে যান।

**AWS EC2** — আপনি `.pem` key দিয়ে connect আছেন, তাই `ssh-copy-id`-কে বলে দিতে হবে কোন key ব্যবহার করবে:

<Callout type="warning">
  নিচের command-এ `-o IdentityFile=` লেখায় **সমান চিহ্ন (`=`)** আছে — এটি বাধ্যতামূলক। `-o "IdentityFile ~/..."` (space দিয়ে) লিখলে SSH এটি বুঝবে না এবং `garbage at end of line` error দেবে।
</Callout>

```bash filename="LOCAL — Terminal"
ssh-copy-id -i ~/.ssh/id_ed25519.pub -o IdentityFile=~/.ssh/myapp-key.pem ubuntu@YOUR_EC2_IP
```

এখন key-টি `ubuntu` user-এর কাছে আছে। সেটি `queen`-এর জন্য সেট করুন:

<Callout type="info">
  এখানে `ubuntu`-এর পুরো `authorized_keys` ফাইল copy না করে **শুধু আপনার নিজের key**-টি নিচ্ছি। কারণ ওই ফাইলে AWS-এর "master key"-ও আছে — সেটি `queen`-এ copy করলে নিজস্ব key ব্যবহারের উদ্দেশ্যই নষ্ট হয়ে যায়।
</Callout>

```bash filename="SERVER — Terminal"
# queen-এর জন্য .ssh ফোল্ডার তৈরি করুন
sudo mkdir -p /home/queen/.ssh

# শুধু আপনার নিজের key (শেষ লাইনটি) queen-এ যোগ করুন
sudo tail -n 1 /home/ubuntu/.ssh/authorized_keys | sudo tee /home/queen/.ssh/authorized_keys

# মালিকানা queen ইউজারকে দিন
sudo chown -R queen:queen /home/queen/.ssh

# সিকিউর পারমিশন সেট করুন
sudo chmod 700 /home/queen/.ssh
sudo chmod 600 /home/queen/.ssh/authorized_keys
```

<Callout type="info">
  **`chmod 700` ও `600` কেন?** SSH ইচ্ছাকৃতভাবে কড়া। `.ssh` ফোল্ডার বা `authorized_keys` ফাইল অন্য কেউ পড়তে পারলে SSH সেটিকে ঝুঁকি ধরে নিয়ে key-টি **সম্পূর্ণ উপেক্ষা করে** — কোনো error message ছাড়াই। "key কাজ করছে না" সমস্যার এটি সবচেয়ে common কারণ।
</Callout>

### Verify Key Login Works

Provider যেটিই হোক, এখন নিজের কম্পিউটার থেকে `queen` হিসেবে login করে দেখুন:

```bash filename="LOCAL — Terminal"
ssh queen@YOUR_SERVER_IP
```

<Callout type="warning">
  পাসওয়ার্ড ছাড়া login **কাজ করছে কিনা এখনই নিশ্চিত করুন**। পরের ধাপে আমরা password login সম্পূর্ণ বন্ধ করে দেব — key যদি তখনো কাজ না করে, আপনি নিজের server থেকেই বের হয়ে যাবেন।
</Callout>

### Disable Password Login

পাসওয়ার্ড লগিন বন্ধ করা অত্যন্ত জরুরি। কিন্তু এখানে একটি ফাঁদ আছে যা অনেক tutorial-এ বলা হয় না।

<Callout type="warning">
  Ubuntu 24.04-এর `/etc/ssh/sshd_config` ফাইলের **শুরুতে** এই লাইনটি থাকে:

  ```
  Include /etc/ssh/sshd_config.d/*.conf
  ```

  এবং অধিকাংশ cloud server-এ `/etc/ssh/sshd_config.d/50-cloud-init.conf` ফাইলে `PasswordAuthentication yes` লেখা থাকে।

  SSH-এর নিয়ম হলো **প্রথম যে setting পায় সেটিই মানে** (first match wins)। তাই আপনি যদি শুধু মূল ফাইলে `PasswordAuthentication no` লেখেন, ওই include করা ফাইলটি আগে পড়া হবে এবং আপনার setting কাজ করবে **না**। Server অরক্ষিত থেকে যাবে, অথচ আপনি ভাববেন secure করেছেন।
</Callout>

প্রথমে দেখুন আপনার server-এ কোথায় কি সেট করা আছে:

```bash filename="SERVER — Terminal"
sudo grep -r "PasswordAuthentication" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
```

যদি output-এ `50-cloud-init.conf`-এ `PasswordAuthentication yes` দেখেন, সেই ফাইলটি এডিট করে লাইনটি `#` দিয়ে comment করে দিন:

```bash filename="SERVER — Terminal"
sudo nano /etc/ssh/sshd_config.d/50-cloud-init.conf
```

এবার নিজের hardening config ফাইল তৈরি করুন:

```bash filename="SERVER — Terminal"
sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
```

নিচের লাইন দুটি লিখুন:

```bash filename="SERVER — /etc/ssh/sshd_config.d/99-hardening.conf"
PasswordAuthentication no
PermitRootLogin no
```

`Ctrl+O`, `Enter` দিয়ে সেভ করুন এবং `Ctrl+X` দিয়ে বের হয়ে আসুন।

এখন config-এ কোনো ভুল আছে কিনা **test করুন**। ভুল থাকলে SSH restart-এ আপনি নিজেই server থেকে বাহির হয়ে যেতে পারেন:

```bash filename="SERVER — Terminal"
sudo sshd -t
```

কোনো output না এলে config ঠিক আছে। এবার SSH restart দিন:

<Callout type="info">
  Ubuntu-তে service-টির নাম `ssh`, `sshd` নয়। অনেক tutorial-এ `systemctl restart sshd` লেখা থাকে — সেটি Ubuntu-তে কাজ নাও করতে পারে।
</Callout>

```bash filename="SERVER — Terminal"
sudo systemctl restart ssh
```

<Callout type="warning">
  **এখনই current terminal বন্ধ করবেন না।** একটি **নতুন** terminal খুলে login হচ্ছে কিনা দেখুন। যদি key কাজ না করে, পুরনো terminal-টি খোলা থাকলে আপনি ভুল ঠিক করতে পারবেন। এটি একটি প্রফেশনাল অভ্যাস — প্রতিটি sysadmin এভাবেই কাজ করেন।

  Password login সত্যিই বন্ধ হয়েছে কিনা verify করুন:

  ```bash filename="LOCAL — Terminal"
  ssh -o PubkeyAuthentication=no queen@YOUR_SERVER_IP
  ```

  `Permission denied (publickey)` দেখলে সফল।
</Callout>

### Configure the Firewall

শুধু প্রয়োজনীয় পোর্টগুলো (২২, ৮০, ৪৪৩) ওপেন রাখুন — বাকি সব বন্ধ:

```bash filename="SERVER — Terminal"
# SSH allow নিশ্চিত করুন (এটি আগে না দিলে নিজেই আটকে যাবেন)
sudo ufw allow OpenSSH

# Web traffic
sudo ufw allow 80
sudo ufw allow 443

# Firewall চালু করুন
sudo ufw enable
```

Status দেখে নিন:

```bash filename="SERVER — Terminal"
sudo ufw status
```

**AWS EC2 ব্যবহার করলে একটি বাড়তি ধাপ** — AWS Console-এ গিয়ে Security Group-এ port 22, 80, 443 allow করা আছে কিনা দেখুন (server তৈরির সময় এটি সেট করেছিলেন)। বাদ পড়লে "Edit inbound rules"-এ গিয়ে যোগ করুন।

<Callout type="info">
  **UFW বনাম Security Group — দুই জায়গায় কেন?**

  - **AWS Security Group** হলো আপনার server-এর "বাইরের গেট" (Cloud Level)।
  - **UFW** হলো server-এর "নিজের দরজা" (OS Level)।

  প্রফেশনাল নিরাপত্তার জন্য উভয় স্তরেই firewall থাকা জরুরি। একে বলা হয় **Defense in Depth** — যেকোনো একটি স্তরে ত্রুটি থাকলেও অন্যটি আপনার server-কে সুরক্ষিত রাখে।
</Callout>

সার্ভার এখন নিরাপদ।

</Steps>

- [ ] SSH key দিয়ে `queen` user হিসেবে পাসওয়ার্ড ছাড়াই লগিন হচ্ছে?
- [ ] `sudo grep -r "PasswordAuthentication" /etc/ssh/sshd_config.d/` দেখাচ্ছে কোথাও `yes` নেই?

- [ ] `sudo ufw status` দেখাচ্ছে port 22, 80, 443 open?
- [ ] AWS ব্যবহারকারী: Security Group-এও এই রুলগুলো আছে?

  এই পেজে আপনি যা করলেন তাকে বলে **Server Hardening**। এটি একটি স্ট্যান্ডার্ড সিকিউরিটি প্র্যাকটিস। পেনিট্রেশন টেস্টাররা যখন কোনো সার্ভারে অ্যাটাক করার চেষ্টা করেন, তারা প্রথমেই দেখেন কোনো ভুল কনফিগারেশন আছে কিনা — যেমন root login খোলা রাখা বা weak password।

  আপনি এই ধাপগুলো সম্পন্ন করার মধ্য দিয়ে সবচেয়ে common attack path-গুলো বন্ধ করে দিয়েছেন। TryHackMe-র **"Linux Privilege Escalation"** room-এ দেখবেন attackers ঠিক এই misconfiguration-গুলোই খোঁজে।
</Callout>
